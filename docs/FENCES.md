# 栅栏：格边阻挡

第二十关新增用户确认的公共栅栏机制。栅栏位于两个正交相邻格的公共边上，不占用其中任何一格；它不是墙、草丛或能量块。

schema 1 使用可选的 `fences` 数组，省略等同空数组。例如第二十关：

```json
"fences": [
  [[0, 3], [0, 4]],
  [[4, 3], [4, 4]]
]
```

`FenceEdges` 将每条边的端点规范化并建立查询索引。端点必须是地图内整数地板坐标、曼哈顿距离为 1；自连接、斜向、跨格、越界、墙端点及正反重复均拒绝。`level.has_fence(a, b)` 与反向查询结果相同。旧关卡不迁移、不新增空字段。

每次方向输入按现有顺序处理：

1. 蓝英雄先检查本次方向的首个可见英雄或水晶。视线不考虑栅栏；合法目标交换两个端点位置，不按中间格逐步行走。墙、草丛、实体能量的遮挡不变，不能穿过这些遮挡交换。
2. 没有发生交换时，校验实际走动。英雄跨栏则拒绝。
3. 红人混合连推时，英雄和链内每个英雄/水晶的起止边都须通过；任何一条边受阻，整步位置、计数和撤销历史均不变。
4. 绿人背后相邻水晶的自动单拉也须校验水晶跨边。拉动跨栏时整个走动/拉动拒绝，不能只让英雄先走。最近水晶后方未跨越的栅栏不妨碍合法单拉。
5. 所有移动合法后，才进入原有统一压力/能量/死亡/毁晶结算和原子撤销。被动移动的英雄不触发能力，C 免费选择与撤销保持当前选择不变。

渲染在公共边绘制双金属横杆、立柱和铆钉，避免把某格涂成障碍；地图卡片也绘制简化格边。栅栏数据不进入格子占用或视线遮挡查询。当前图的 F1 为 16↔21、F2 为 20↔25；没有压力板或能量块。

## 验证

- `tests/fence_regression.gd`：数据校验、对称查询；四方向与三英雄的正反阻挡；混合长列任一参与边阻挡的原子性；绿人单拉跨栏与未跨边；蓝人跨栏英雄/水晶交换、没有目标仍受阻、其他遮挡优先和最近目标。
- `tests/north_20_regression.gd`：全部 25 格、三英雄/两水晶/三终点/两边初值；合法路线、6 次跨栏交换、无目标蓝人受阻、30 次完整撤销、免费 C 与重开/切关隔离。
- `tests/north_20_scene.gd`：真实按下/释放及屏幕按钮、长按/echo 防重、C、撤销与胜利；1280×820 和 960×615 下三种当前高亮和格边金属像素验证。
- `tests/navigation_scene.gd`：全部 20 关进入/返回，5000 条合成数据仍复用有界卡片池；不向正式目录加入虚构关卡。
- `tools/check_walkthroughs.py`：独立重算所有移动参与者跨边、交换视线与状态，不依赖 Godot 模型输出判定合法；保留旧视频回放兼容。

独立五对象身份 BFS 在首次胜利停止：展开 28679、访问 34057 状态，找到 30 次实际行动和 13 次免费切换，2 推 / 2 拉 / 11 交换，其中 6 次交换跨过栅栏。路径保存在 `levels/solutions/north_20.json`，不宣称最短或穷举所有状态。实际运行结果见 [验证记录](VERIFICATION.md)。
